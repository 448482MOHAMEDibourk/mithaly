# قواعد التدفق الطبقي (Layered Flow Rules)

هذا المستند يصف قواعد انتقال المهام بين الطبقات في Mithaly، بما في ذلك سيناريوهات الفشل، دور `INFLECTION_POINT`، ومتطلبات الحفظ والتوثيق.

مبادئ عامة:
- المرور الطبقي متسلسل: `Gaps` → `Planning` → `Safe Execution` → `Feedback`.
- لا يتم القفز إلى طبقة أعلى إلا عبر الانتقال الرسمي من الطبقة الوسيطة.
- لا تعود المهمة عكسيًا إلا بهدف مراجعة نتائج الطبقة السابقة.
- الاستثناءات: طبقة `Feedback` يمكن أن تكسر الترتيب إذا فشلت المهمة أو لتحديث السياق.

تعريفات مختصرة:
- `INFLECTION_POINT`: نقطة إيقاف/مراجعة تُجري snapshot للسياق الحالي وتطلب مراجعة بشرية أو قرارًا آليًا مُصرحًا.
- `حالة الفشل`: قيمة مرجعية/عتبة تُعرّف متى يعتبر الإجراء فشلًا (مقاييس/اختبارات/مؤشرات).

سلوك كل طبقة:

1) طبقة الفجوات (Gaps)
- دورها: كشف الفجوات، تحليل الأسباب الجذرية، ترتيبها، وإعداد حزمة مهام مرتبة لطبقة التخطيط.
- مكونات:
  - محلل الفجوات: كشف + تحليل جذور.
  - مُرتّب الأولويات: سكربت القياس و المعايير والنتائج (تُحفظ المعايير كمرجع).

2) طبقة التخطيط (Planning)
- دورها: إنتاج خطة استباقية لتأمين التنفيذ وإجراء اختبارات مبدئية في بيئة افتراضية.
- آليات:
  - التخطيط المعرفي (theoretical)
  - التخطيط السياقي/الواقعي (realistic)
  - الاختبار في بيئة افتراضية

3) طبقة التنفيذ الآمن (Safe Execution)
- دورها: تنفيذ الخطة بعد استنفاد درجات الحيطة، مع يقظة وإبلاغ طبقة التخطيط وطلب إذن عند الحاجة.
- متطلبات:
  - تنفيذ بمراقبة، إمكانية التراجع/الاختبار بعد التنفيذ.

4) حلقة التغذية الراجعة (Feedback)
- دورها: تدوين نتائج الاختبارات، حفظ أنماط النجاح والفشل، وتحديث السياق والسياق المعماري.

سيناريوهات التدفق الرئيسية:
- نجاح: المسار الطبيعي من Gaps → Planning → Execution → Feedback.
- فشل: اعتمادًا على مكان الفشل:
  - فشل في التنفيذ: وقف سريع، احتواء، وإحالة إلى Feedback مع سجل الفشل.
  - فشل في الاختبار الافتراضي: العودة لإعادة التخطيط ثم تمرير نتائج إلى Feedback.
  - فشل في التخطيط: تبادل بين التخطيط المعرفي والواقعي (حتى مرتين كحد أقصى). إذا رُفضت المهمة نهائيًا تُرسل إلى Feedback مع تعليل. إذا قُبلت لكن رُفض ترتيبها يُطلب تعديل معايير الترتيب.
  - حالات طارئة أو عجز التنفيذ: تُصنّف في ملف الطوارئ وتُناقش آليات التفويض.

وثائق ومخارج مطلوبة لكل انتقال:
- كل انتقال يجب أن يُسجَّل بالحقول التالية (للاطّلاع والتدقيق):
  - `from_layer`, `to_layer`, `reason`, `metrics`, `timestamp`, `actor`, `outcome`, `emergency`, `approved_by`.
- نماذج الانتقال تحفظ في `docs/context/` وتُرمز بالبِرُوفانس (provenance).

المطالب التنفيذية:
- تنفيذ مخطط JSON Schema لانتقال الطبقات في `docs/context/schemas/layer_transition_schema.json`.
- تضمين قواعد الـ- INFLECTION_POINT and snapshot policy: see `docs/MITHALY_CONSTITUTION.md`

## 4. المفسر الدستوري (The Constitutional Interpreter)

تعمل هذه الوثيقة كجسر (Bridge) لتفسير المبادئ الراسخة في الدستور وتحويلها إلى إجراءات تقنية:

| مبدأ الدستور | التفسير الإجرائي (Workflow) |
| :--- | :--- |
| مصدر الحقيقة (SOT) | مرجع معزول للمستخدم؛ لا يُستدعى برمجياً. |
| المادة 2: حتمية الانعطاف | تفعيل عقدة `INFLECTION` وتسجيل سجل `outcome: blocked`. |
| المادة 4: الإدراك قبل الإرادة | إلزامية استدعاء `probe()` قبل الانتقال من Planning إلى Execution. |
| المادة 5: قداسة النصوص | منع عمليات `os.remove` أو `write` على ملفات الدستور والـ workflow. |
